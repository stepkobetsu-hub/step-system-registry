## 2026-08-22〜23 の主な復旧内容

### 1. 保存基盤

通常編集はCloudflare WorkerからD1へ直接保存する。Google Apps Scriptはログイン・互換用途に限定し、進捗・目標範囲・宿題の通常保存でGoogle応答を待たない。

- 進捗 debounce: 300ms
- 目標範囲 debounce: 350ms
- 宿題の古いlocalStorageキャッシュは復元しない
- 保存ボタン必須ではない

### 2. 宿題チェック

生徒の宿題操作と先生確認を分離した。

- 生徒のチェックON: `DECLARED_DONE`
- 生徒のチェックOFF: `UNINPUT`
- 未チェック時の表示: `チェック`
- チェック後の表示: `宿題済み`
- 生徒操作で `teacher_status` を変更しない
- 先生確認は講師・管理者操作だけで変更する
- 先生確認済み後は生徒側で変更不可
- 保存APIは保存結果の `homework` を返し、画面キャッシュへ即時反映する

宿題データ保全監査では、旧 `homework_records` と `v3_homework_snapshot` の2,271件について status の欠落・不一致は0件だった。監査時点のV3 homework overrideはダミー1320のテスト操作だけで、本物の生徒で「実施済み→未入力・未実施」へ落ちた疑わしいケースは0件だった。

### 3. 目標範囲・進捗データ復元

V3初期移行後、一部生徒で旧画面と進捗率が大きく違うことを確認した。原因は、旧画面が使っていたSupabaseの `student_targets` / `learning_progress` と標準範囲ロジックを、V3初期移行で完全には再現できていなかったこと。

復旧では、旧Supabaseの正しいデータを基準に以下を実施した。

- 旧標準範囲＋生徒別ON/OFFから正しい目標範囲を再生成
- V3目標スナップショットを正しい目標へ復元
- Supabaseの旧学習進捗3,536件をV3へ結合
- V3切替後に入力された新しい進捗は優先して保持
- 目標範囲のV3 override 99件も保持
- 宿題データには触れない
- 進捗集計は `unit_id` が全体一意である前提へ統一し、教材シリーズ表記差で学習済みが落ちないよう修正

復元後の本番 `/health`:

- 進捗: 3,540
- 目標: 6,555
- 宿題: 2,271

### 5. 生徒トップの進捗グラフ表示高速化（2026-08-23）

田中彗翔（1100）のように進捗量が多い生徒で、宿題一覧はすぐ表示される一方、上部の進捗グラフだけ約1分遅れて表示される報告があった。

調査結果:

- 田中1100の本番 `getStudentDashboard` 自体は3回計測で **0.756秒 / 1.026秒 / 0.862秒**
- レスポンスは約535KB、`selectableUnits=356`、目標単元70、進捗表示121/70を正常返却
- したがって「進捗量が多いからD1集計に1分かかる」のではなかった
- 画面側で宿題表示を先に行った後、グラフ用 `getStudentDashboard` の取得開始が遅れる経路が残っていた

対策:

- 宿題の表示・保存処理は変更しない
- 生徒画面を開いた直後に、グラフ用 `getStudentDashboard` を先行開始する
- 宿題表示とグラフ取得を独立させ、グラフが宿題処理の後ろで待たないようにする
- 配信HTMLで `eagerDashboardPromise` の先行取得処理を確認してから本番反映

反映結果:

- 本番Version ID: `b6ed5627-f360-4ba2-8e09-92e9d5d71340`
- 本番 `/health`: 生徒34・進捗3540・目標6555・宿題2271で変更なし
- 利用者実画面で「速くなった」と確認済み

## 変更時の注意

- `unit_id` は全体一意として進捗集計する。教材シリーズを混ぜた複合キーで完了数を落とさない。
- 旧Supabaseの目標・進捗は、V3復旧時の正解データとして保全する。
- 宿題表示とグラフ取得は独立させる。宿題が速い場合にグラフ取得を宿題の後ろへ戻さない。
- 本物の生徒データを使った試験は避け、通常は1320を利用する。ただし表示性能の実測では、読み取り専用で1100等の代表データを使うことがある。
- パスワード、API token、セッショントークンをGitHub・台帳へ記載しない。
- 大規模な全生徒E2Eより、代表5名＋1320の最小確認を優先する。
